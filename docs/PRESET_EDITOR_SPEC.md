# Техническое задание на редактор пресетов

Дата: 18 октября 2026 года. Статус: исходное ТЗ реализации, подготовленное с участием
системного аналитика; редактор реализован по этому документу. Раздел 2 сохраняет
описание проекта до перехода. Действующие команды и контракт находятся в
[DEVELOPMENT.md](DEVELOPMENT.md) и [API.md](API.md); результаты проверок фиксируются
отдельно и не подразумеваются самим статусом ТЗ.

Редактор позволяет создавать и изменять пресеты через браузер. Пользовательские
данные хранятся отдельно от поставляемых файлов и сохраняются при обновлении
checkout или Docker-образа. Обновление встроенного пресета не меняет параметры
его пользовательской версии без явного действия пользователя.

## 1 Цель и границы сохранности

Обязательный результат: после сохранения пресета, обновления приложения и
перезапуска остаются его ID, название, описание, параметры и пользовательский
выбор пресетов по умолчанию. Уже созданные задания сохраняют прежние параметры
и подписи независимо от последующих изменений каталога.

Гарантия распространяется на обычный `git pull`, пересборку образа, `docker
compose pull` и пересоздание контейнера при сохранении того же хранилища данных.
Для локального запуска каталог данных должен оставаться на диске; для Docker
нужно повторно подключать тот же том или bind-mount `settings`. При смене имени
Compose-проекта необходимо явно подключить прежний том либо перенести данные.

Удаление тома, `docker compose down -v`, ручное удаление данных и
`git clean -fdx` внутри checkout с локальным хранилищем требуют восстановления
из резервной копии. Приложение не может восстановить правки, потерянные до
миграции. Инструкция первого перехода должна начинаться с резервной копии
старых YAML **до обновления Git или контейнера**.

## 2 Основания в текущем проекте

- [app/models/presets.py](../app/models/presets.py) читает четыре слоя YAML:
  `video`, `audio`, `subtitles`, `data`. Менеджер создаётся при импорте;
  в каждом слое требуется ровно один `default: true`.
- До перехода поставляемые файлы лежали в отслеживаемом Git каталоге
  `presets/` (теперь [app/builtin_presets/](../app/builtin_presets)). Основной, dev, prod, Windows, multiarch и тестовый
  Compose монтируют `./presets:/app/presets`. Registry и Unraid обычно используют
  файлы из образа. Редактирование этого каталога связывает пользовательские
  данные с поставкой и создаёт конфликты при обновлении.
- `reload_presets()` сначала очищает рабочие словари. Для изменения каталога
  при работающем сервере такая последовательность непригодна: читатели могут
  увидеть пустой или частично загруженный каталог.
- [app/routes.py](../app/routes.py) выдаёт `/api/presets` и
  `/api/presets/resolve`, выбирает параметры для upload и internal encode.
  Часть значений по умолчанию берётся из импортированных `DEFAULT_*`, которые
  не изменяются после загрузки модуля.
- [app/models/job.py](../app/models/job.py) уже хранит `ffmpeg_params`,
  а [app/job_store.py](../app/job_store.py) сохраняет их в SQLite. Однако
  `Job.display_label()` заново получает названия из текущего каталога.
- [app/templates/index.html](../app/templates/index.html) применяет пресеты
  через inline JavaScript. Для subtitles/data подставляет `copy`, а при пустом
  bitrate/sample_rate может оставлять значения предыдущего audio-пресета.
- [app/static/js/upload.js](../app/static/js/upload.js) фиксирует поля формы
  на отправку пачки. На сервере chunk manifest хранит только имя и количество
  частей; параметры заново разрешаются на каждом чанке.
- [app/settings_store.py](../app/settings_store.py) использует отдельный
  JSON-файл и `os.replace`; том `/app/settings` уже существует во всех вариантах
  развёртывания. Пользовательские данные не требуют новой зависимости.

## 3 Состав первой версии

Реализовать одну страницу `/presets` в существующем Jinja/Bootstrap интерфейсе,
без npm и отдельного frontend-приложения. В навигацию добавить «Пресеты».

Пользователь может:

1. Просматривать четыре слоя, искать по ID/названию, видеть источник и default.
2. Создавать пресет с нуля или копировать существующий.
3. Менять название, описание и поддерживаемые параметры.
4. Сохранять пользовательскую версию встроенного пресета под прежним ID.
5. Назначать default отдельно для каждого слоя.
6. Сбрасывать пользовательскую версию до текущего встроенного пресета.
7. Удалять собственные пресеты с явным подтверждением.
8. Сравнивать пользовательскую версию с текущей поставкой.
9. Экспортировать пользовательский каталог и импортировать его с предварительной
   проверкой и просмотром конфликтов; переносить старые YAML.

На главной странице по-прежнему выбираются video/audio и `audio_downmix`.
Subtitles/data берутся из defaults редактора. Отдельный выбор этих двух слоёв
на каждое задание в первую версию не входит.

Метаданные MKV, nickname, параметры ресурсов `cpu_threads`, `thread_queue_size`,
`x265_pools` и `audio_downmix` остаются настройками приложения/отправки задания.
Они не становятся полями слоя пресета. `hevc_remux` сохраняет существующее
поведение перекодирования; этап MKVToolNix остаётся отдельным.

За рамками первой версии: произвольные команды FFmpeg, новые видеокодеки и
контейнеры, совместное редактирование в реальном времени, несколько серверных
процессов, автоматическое слияние с новой поставкой, полная история версий
с интерфейсом отката. Резервные копии и обнаружение конфликтов обязательны.

## 4 Архитектура хранения

### 4.1 Поставляемые пресеты

Перенести единственную каноническую копию YAML из `presets/` в
`app/builtin_presets/{video,audio,subtitles,data}/`. Эти файлы отслеживаются Git
и попадают в образ вместе с `app/`. Python и Docker читают один и тот же набор.
Приложение никогда не записывает в этот каталог; в runtime допустим read-only.

Старый `/app/presets` использовать только как явно выбранный источник миграции.
Старый mount не должен скрывать новую поставку. Не создавать named volume поверх
встроенных пресетов: он закрепит старую поставку и скроет обновления образа.
Функцию генерации YAML при отсутствии слоя убрать из production-загрузки:
ошибка поставки должна диагностироваться, а не исправляться записью в исходники.
Генератор при необходимости оставить отдельным инструментом разработки.

### 4.2 Пользовательский каталог

Основной файл: `/app/settings/presets/catalog.json`.
Переменная окружения: `USER_PRESETS_PATH`, абсолютный путь к файлу.
Для локального запуска документировать
`USER_PRESETS_PATH="$PWD/settings/presets/catalog.json"`.
Переменная независима от `APP_SETTINGS_PATH` и `JOB_STORE_PATH`:
изменение одного пути не переносит остальные данные.

Файл содержит `schema_version`, уникальную `revision`, все пользовательские
записи, выбор defaults и отметки завершённых миграций. Изменение одного пресета
и связанного default фиксируется одной записью всего файла.

Выбор: единый JSON вместо отдельного YAML на пресет. Для небольшого каталога
это даёт атомарное изменение пресетов и defaults без многофайловой транзакции.
Отдельная SQLite также решает эту задачу, но здесь не требуется: переносимый
каталог не зависит от истории заданий. В `app_settings.json` каталог не добавлять:
его существующий reader сохраняет только известные поля.

Резервные копии хранить рядом в `backups/`, последние 20 успешных состояний;
архивы исходных legacy YAML сохранять отдельно без автоматического удаления.
Резервные копии на том же диске защищают от ошибочной правки, экспорт на другой
диск нужен для восстановления после потери тома.

### 4.3 Запись и идентичность пресета

Ключ пресета — пара `(layer, id)`. Одинаковый ID в разных слоях допустим.
ID неизменяем после создания; изменение названия не меняет ID.
Новым пользовательским пресетам выдавать ID вида `user_<uuid_hex>`.
Префикс `user_` зарезервировать в поставке. Legacy ID сохранять без переименования,
чтобы не сломать существующие интеграции; возможные коллизии обрабатывать явно.
`custom` зарезервирован для разовых параметров задания и не может стать ID пресета.

Типы записей:

- `custom` — самостоятельный пользовательский пресет;
- `override` — полная пользовательская версия встроенного пресета с тем же ID.

`definition` содержит полное нормализованное определение, включая `null`
опциональных полей. `default` внутри определения не хранится: он вычисляется
по defaults каталога. Отсутствие поля при замене определения означает его
очистку по схеме, а не наследование значения встроенного пресета.

У `override` сохранять `base_snapshot` и `base_fingerprint` встроенного
определения, относительно которого сделана первая правка. Обычное повторное
сохранение не меняет базу сравнения. Для импортированной legacy записи база
может быть неизвестна; использовать `null` и статус «База версии неизвестна».

Пример фрагмента каталога, не полный список слоёв:

```json
{
  "schema_version": 1,
  "revision": "a6562059-7324-45aa-aac2-903d3bcb09c1",
  "defaults": {
    "video": "hevc_auto_level_rip",
    "audio": null,
    "subtitles": null,
    "data": null
  },
  "entries": [
    {
      "layer": "video",
      "id": "hevc_auto_level_rip",
      "kind": "override",
      "definition": {
        "name": "Мой HEVC",
        "description": "Пользовательские параметры",
        "video_codec": "libx265",
        "output_format": "matroska",
        "preset": "slow",
        "crf": "21",
        "pixel_format": "yuv420p10le",
        "x265_params": null,
        "tune": "animation",
        "video_map": "0:v:0"
      },
      "base_snapshot": null,
      "base_fingerprint": null
    }
  ],
  "migrations": []
}
```

`revision` — новый UUID после каждой успешной мутации, включая восстановление
резервной копии. При отсутствующем файле использовать фиксированную исходную
revision `empty-v1`, одинаковую между запусками и CLI preview/apply. Первый UUID
создавать только при первой успешной записи. Клиентский `catalog_revision` — непрозрачный SHA256 от версии
схемы, канонических встроенных определений/defaults и пользовательского состояния.
Он меняется и при обновлении поставки, даже если пользовательский JSON не менялся.
Канонизация: UTF-8 JSON, сортировка ключей и записей по `(layer,id)`, фиксированные
разделители, нормализованные типы; комментарии YAML и порядок файлов не учитываются.

## 5 Объединение и обновление поставки

Собрать неизменяемый снимок каталога: встроенные определения → полные
пользовательские версии → самостоятельные записи → effective defaults.
Слияния отдельных полей или строк `x265_params` между версиями нет.

Правила обязательны:

1. Встроенный пресет без пользовательской версии получает изменения поставки.
2. Пользовательская версия полностью перекрывает встроенный пресет и сохраняет
   своё поведение. При изменении базы показывать «Встроенный пресет обновлён»
   и различия текущей поставки, сохранённой базы и пользовательской версии.
3. Сброс удаляет только `override` и сразу открывает текущую встроенную версию.
   Default на этот же ID сохраняется. Подтверждение перечисляет меняющиеся поля.
4. Если встроенный пресет удалён, его `override` остаётся рабочим под прежним ID
   со статусом «Нет в текущей поставке». Сброс недоступен; можно скопировать
   или удалить его по правилам пользовательского пресета.
5. Переименование встроенного ID считается удалением и добавлением.
   Автоматически переназначать ID нельзя.
6. Если новый встроенный ID совпал с legacy `custom`, пользовательская запись
   остаётся приоритетной. Показать конфликт источников; сброс до поставки
   разрешать только после экспорта/преобразования в явный `override` с подтверждением.
7. Обновление не записывает пользовательский JSON лишь ради изменения
   fingerprint или появления предупреждения. Новое состояние поставки
   вычисляется при загрузке и не требует изменения пользовательских данных.

Для defaults `null` означает «следовать default поставки», строка — явный
пользовательский выбор. В effective каталоге ровно один default каждого слоя;
флаги `default` в API вычисляются из него. Два default из файлов не должны
просачиваться в effective состояние.

Удаление собственного default требует `replacement_default_id` того же слоя
в той же операции; иначе HTTP 409. Удаление встроенных пресетов не поддерживать.
Для отмены пользовательского выбора есть действие «Default поставки».

Если явный default ссылается на отсутствующую запись, каталог невалиден:
не выбирать другой пресет молча. Если default структурно валиден, но кодек
недоступен на машине, сохранять выбор, показывать причину и блокировать запуск
с ним до явного выбора доступного пресета.

## 6 Сохранение и работающий сервер

Выделить `PresetStore` для диска и сервис каталога для валидации, effective
снимков и операций. Существующий `preset_manager` оставить стабильным фасадом,
чтобы импортирующие модули не держали ссылку на устаревший менеджер.

Алгоритм мутации под одним `threading.RLock`:

1. Проверить актуальную версию `If-Match`, собрать копию нового состояния,
   полностью провалидировать записи, defaults и effective снимок.
2. Сохранить последнюю корректную версию в резервную копию. При первой записи
   иметь возможность восстановить исходное пустое пользовательское состояние.
3. Записать новый JSON в уникальный временный файл в том же каталоге,
   выполнить `flush` и `fsync`, заменить основной через `os.replace`.
   На поддерживаемой ОС выполнить `fsync` родительского каталога.
4. Заменить единую ссылку на готовый effective снимок до освобождения lock.
   Вернуть новую версию, затем отправить уведомление клиентам.

Читатель захватывает ссылку на снимок под lock и использует её всю операцию.
Не держать lock при копировании видео, вычислении SHA256 или кодировании.
Одновременный GET видит целиком старое либо целиком новое состояние.
Не использовать последовательность `clear()` → повторная загрузка.

Ни запись на диск, ни сигнал Socket.IO не должны предшествовать полной валидации.
Ошибка до `os.replace` оставляет прежние данные/снимок; ошибка доставки события
после commit не отменяет сохранение. Если сбой случился после замены файла и
результат долговечности неизвестен, ответить 503 `save_result_unknown`, перечитать
файл, согласовать снимок с диском и предложить GET перед повтором. Нельзя обещать
«изменения не сохранены», когда файл уже мог быть заменён.

При невозможности записи возвращать 503 без ложного сообщения об успехе.
На старте отличать отсутствие каталога от повреждённого JSON: отсутствие
означает чистую установку; повреждение/неподдерживаемая версия не означают
пустой каталог. Не заменять повреждённые данные и не восстанавливать backup молча.
Страница диагностики/редактор должны показать ошибку и путь восстановления.
На работающем сервере сохранить последний валидный снимок; на новом старте
с повреждённым user store блокировать создание новых заданий до восстановления,
сохраняя доступ к истории и диагностике. Уже принятые задания используют свои снимки.

Поддерживается один серверный процесс, как и в текущем проекте.
Миграционные утилиты запускаются при остановленном сервере. Ручная правка
JSON во время работы не поддерживается; импорт производится через API.
Синхронизация между несколькими WSGI workers не входит в эту реализацию.

## 7 Схема и валидация

Один валидатор использовать для API, user store и миграции. Безопасный разбор
YAML сохраняется через CSafeLoader/SafeLoader; Python tags запрещены.
Дубли ключей JSON/YAML, дубли `(layer,id)`, неизвестные поля и не-объекты
отклоняются с указанием записи и поля, а не перезаписываются последним значением.

Общие ограничения: ID 1–64 символа `[A-Za-z0-9_-]`, имя 1–120 символов после
trim, описание до 4000, `x265_params` до 4096. Запретить управляющие символы
кроме перевода строки/табуляции в описании. Максимум 500 пользовательских записей
и 5 MiB JSON каталога; одно определение до 64 KiB. Превышение HTTP body — 413.
Пути хранилища приходят только из конфигурации сервера, не из тела CRUD-запроса.

### 7.1 Поля слоёв

- **video:** обязательные `video_codec=libx265`, `output_format=matroska`;
  опциональные `preset`, `crf`, `pixel_format`, `x265_params`, `tune`, `video_map`.
  Пустые опциональные поля нормализуются в `null`; это означает автонастройку,
  без восстановления значений старого пресета. Для `video_map=null` сохранить
  существующий fallback `0:v:0?` в команде воркера.
- **audio:** `codec`, `bitrate`, `sample_rate`, `vbr`, `audio_map`.
  Кодеки первой версии: `copy`, `aac`, `libfdk_aac`, `libopus`, `null`.
  UI alias `opus` нормализуется в `libopus`. Пустая пара `codec/audio_map`
  означает отсутствие аудио. Для `copy` и отсутствия аудио поля encode
  `bitrate/sample_rate/vbr` должны быть `null`.
- **subtitles:** `subtitle_map`, `subtitle_codec`; кодеки `copy`, `ass`, `srt`
  либо `null`.
- **data:** `data_map`, `data_codec`; кодек `copy` либо `null`.
  Этот слой соответствует вложениям `0:t?`, а не произвольным data-потокам.

У audio/subtitles/data codec и map заполнены вместе либо оба `null`.
`remove` из UI нормализовать в пару `null`. Строки `"null"`/`"None"` не
использовать как значения нового каталога; legacy import нормализует их явно.

CRF — целое 0–51, canonical строка или `null`; bool, дроби и NaN отклоняются.
Скорости, pixel format и tune — значения существующих select главной страницы;
`tune=none` нормализуется в `null`. Битрейт — целое 8–1536 kbit/s с суффиксом
`k`, частота — целое 8000–192000 Hz в canonical строке, VBR — boolean или `null`.
Проверка схемы не обещает совместимость любого битрейта/частоты с каждым кодеком.
Фактические ограничения сборки и исходника проверяются при кодировании;
недоступный FDK отмечается до отправки задания.

Карты ограничить одним входом и типом потока: `0:v`, `0:a`, `0:s`, `0:t`
с необязательными `:N` и `?`, где N — неотрицательный индекс.
Нельзя передавать другой input, отрицательные карты, дополнительные аргументы,
filtergraph или имена выходных файлов. Downmix сохраняет более узкие правила
существующего `parse_audio_map`, включая запрет stereo с copy/без аудио.

`x265_params` остаётся расширенным строковым полем, поддерживаемым текущим
воркером. Проверять размер и управляющие символы, передавать одним аргументом
через существующий список `argv`, без shell и без разбиения строки на новые
аргументы FFmpeg. Не вводить whitelist только по параметрам штатных YAML:
это заблокирует перенос уже работающих пользовательских настроек. Проверка
редактора структурная; семантические ошибки параметров x265 диагностируются
кодировщиком и попадают в лог задания. Не добавлять автоматический запуск
FFmpeg или чтение указанных в параметрах файлов при просмотре/сохранении пресета.
Существующий разовый custom encode не расширять в рамках задачи.

### 7.2 Семантика отсутствия аудио

При отсутствии аудио по `codec/audio_map` выбирать subtitles/data `none`
независимо от ID audio-пресета. Так копия «Без аудио» под `user_*` получает
то же поведение, что текущий `audio_id=none`. Служебные subtitles/data `none`
должны существовать и оставаться пустыми; менять разрешено только их подписи.
Встроенный audio `none` также сохраняет семантику отсутствия аудио.
Проверять эти инварианты при любой мутации всего каталога.

### 7.3 Доступность и пользовательский ввод

Сохранение структурно корректного FDK-пресета допускается без установленного FDK:
такой пресет переносим между машинами. `available=false` запрещает encode
и назначение нового default через редактор, но не просмотр/изменение/экспорт.
При потере FDK уже сохранённый default не заменяется автоматически.
В импортированном каталоге недоступный default разрешён с явным предупреждением.

Имена и описания выводить как текст, экранировать в карточках, таблицах,
подтверждениях и сообщениях. Редактор использует текущую модель доступа локального
приложения; новую систему пользователей в задачу не включать. Записывающие
endpoints принимают только JSON. Запросы с чужим `Origin` отклонять; для своего
браузера использовать проверку Origin и CSRF token. Для CLI без Origin
сохраняется прямой JSON API. Не расширять текущий список CORS origins ради редактора.
Браузер получает токен в HTML страницы редактора и отправляет заголовком
`X-CSRF-Token`; токен привязан к серверной сессии и не входит в экспорт.

## 8 HTTP контракт редактора

Новые методы отделить префиксом `/api/preset-editor`, чтобы не менять значения
существующих маршрутов. Все GET возвращают `catalog_revision` и сильный
`ETag: "<catalog_revision>"`; мутации требуют точного `If-Match`.
Проверка версии выполняется под тем же lock, что сохранение.
Для новой записи также требуется версия каталога. `If-Match: *` не поддерживать.

- `GET /api/preset-editor` — четыре слоя, effective defaults и пользовательские
  selections, `catalog_revision`, доступность хранилища и предупреждения.
- `GET /api/preset-editor/<layer>/<id>` — effective определение, `source`
  (`builtin`, `override`, `custom`), флаги `orphaned`, `builtin_changed`,
  `base_unknown`, текущая/сохранённая база, различия и доступные действия.
- `POST /api/preset-editor/<layer>` — `{definition, set_default?}`;
  сервер назначает `user_*` ID, возвращает 201 и `Location`.
- `PUT /api/preset-editor/<layer>/<id>` — `{definition, set_default?}`;
  полностью заменяет определение. Для builtin создаёт `override`, для остальных
  обновляет запись; неизвестный ID не создаётся, а даёт 404.
- `POST /api/preset-editor/<layer>/<id>/reset` — удаляет `override` при наличии
  встроенной базы. Для неизменённого builtin — успешная операция без изменения
  версии; для custom или отсутствующей базы — 409.
- `DELETE /api/preset-editor/<layer>/<id>` — удаляет custom или orphaned override;
  optional JSON `{replacement_default_id}` обязателен при удалении default.
  Обычный builtin/override не удаляется: 409 с предложением сброса.
- `PUT /api/preset-editor/defaults` — `{defaults: {video?, audio?, subtitles?, data?}}`;
  атомарно меняет перечисленные selections, `null` возвращает default поставки.
  Отсутствующие слои оставляет без изменений, пустой объект — 400.
- `GET /api/preset-editor/export` — переносимый JSON user store и версия схемы,
  без путей файлов, CSRF token и информации о заданиях; файл скачивается.
- `POST /api/preset-editor/import/preview` — `{catalog, mode, import_defaults?}`;
  проверка без записи,
  возвращает additions/changes/conflicts/default changes, warnings, digest
  нормализованного кандидата и версию каталога, на которой строился просмотр.
- `POST /api/preset-editor/import` — `{catalog, mode, import_defaults?, preview_digest}`;
  `mode=merge` добавляет записи, а при совпадении ID с отличающимися данными
  даёт 409 без записи; `mode=replace_user_catalog` целиком заменяет user state
  после отдельного подтверждения в UI. Для обоих режимов preview обязателен;
  сервер пересчитывает digest и сверяет If-Match. Экспортированная `revision`
  не принимается как новая серверная версия, всегда создаётся новый UUID.

Digest preview связывает mode, `import_defaults`, target `catalog_revision`
и полный нормализованный результат. В merge существующие defaults по умолчанию
сохраняются. Только при `import_defaults=true` принять явные строковые selections
импорта; `null` не отменяет текущий выбор. Если существующий явный selection
отличается, показать конфликт и вернуть 409 без записи. Для замены каталога
принимаются все импортированные selections, включая `null`; отдельный флаг
в этом режиме не используется. Совпавшие определения и selections без изменений
не создают новую revision. Метаданные migration из импорта не должны обходить
проверки или инициировать повторное чтение исходных файлов.

Успешные мутации, кроме создания, возвращают 200 с актуальным объектом/состоянием
и новой версией. Встроенная база при импорте используется только для сравнения:
приоритет имеют полные пользовательские определения. Нельзя импортом добавлять
произвольный путь чтения YAML; legacy импорт выполняется отдельной утилитой.

Ошибки имеют единый формат:

```json
{
  "error": "Пресеты изменены в другой вкладке. Обновите данные и сравните правки.",
  "code": "catalog_revision_conflict",
  "catalog_revision": "текущая версия",
  "fields": {}
}
```

Коды: 400 — схема/значения/неверный JSON; 404 — слой или запись не найдены;
409 — конфликт ID, default или недопустимое действие; 412 — устаревший If-Match;
428 — If-Match отсутствует; 413 — лимит тела; 415 — неверный Content-Type;
403 — проверка Origin/CSRF; 503 — недоступное/повреждённое хранилище,
неподдерживаемая версия схемы либо неопределённый результат записи.
Для 412 использовать `code=catalog_revision_conflict`.

Существующий `GET /api/presets` сохраняет `videos`, `audios`, `defaults`
и `available` у audio. Дополнительно возвращает `catalog_revision` и ETag;
поля потребления редактора выдаёт отдельный API. `GET /api/presets/resolve`
сохраняет прежние ключи, добавляет версию и разрешённые subtitles/data с ID.
Известные ошибки старого API сохраняются: неизвестные ID в resolve — 404,
в encode — 400. Новые ID доступны через прежние upload/internal endpoints.

## 9 Задания и загрузка файлов

### 9.1 Снимок задания

В момент приёма задания одним обращением к одному снимку каталога получить:
IDs всех четырёх фактически выбранных слоёв, названия, полные `ffmpeg_params`,
`audio_downmix`, `catalog_revision` и fingerprints выбранных определений.
Принудительный выбор `none` у subtitles/data должен попасть в provenance.
Параметры хранить только в существующем `Job.ffmpeg_params` — это единственный
источник параметров для worker. Новое `preset_snapshot` содержит IDs, имена,
источники, fingerprints, версию и готовую подпись, без второй копии params;
в SQLite оба поля попадают через существующий JSON record.

Worker использует только сохранённые параметры. Переименование, сброс,
смена default и удаление пресета не меняют planned/in_progress/done Jobs
и не требуют запрета удаления пресетов, использованных в истории.

Для старых записей Job новое поле опционально. Не восстанавливать параметры
через новый каталог: сохранённые `ffmpeg_params` остаются источником истины.
Если исторических названий нет, показывать сохранённые ID и отметку
«Название на момент создания не сохранено», а не выдавать актуальное имя
за историческое. Разовые `custom` задания сохраняют прежнюю подпись.
Если в старой записи отсутствуют или повреждены сами `ffmpeg_params`, пометить
эту запись ошибкой восстановления, не выполнять resolve и не останавливать
чтение остальных Jobs. Рабочая очередь не восстанавливается автоматически.

Все точки выбора defaults в routes и Job перевести на снимок каталога,
включая JSON aliases `video`/`audio`, multipart и default аргументы функций.
Импортированные `DEFAULT_*` не должны определять новые задания после смены
default. Старые записи с ID продолжают восстанавливаться независимо от каталога.

### 9.2 Версия отправки и чанки

UI получает `catalog_revision` вместе с применёнными полями формы и фиксирует
её в `captureEncodingParameters()` на всю браузерную пачку. Поле находится вне
основной формы — явно добавить его в `addFormDataToFormData()`.
Если версия изменилась до начала новой загрузки/запроса encode, сервер отвечает
409 `preset_catalog_changed` до записи новых данных и создания Jobs.

Для уже начатой загрузки по `file_id`:

1. На первом принятом чанке под существующим lock проверить версию, разрешить
   параметры один раз и сохранить в `upload.json` версию manifest, snapshot,
   fingerprint исходных параметров запроса, имя и количество частей.
2. Следующие чанки сверяют fingerprint и используют manifest без нового resolve,
   даже если каталог изменён или пресет уже удалён. Изменение параметров при том
   же `file_id` — 409; принятые части остаются на диске.
3. Итоговая сборка создаёт Job из manifest. Повтор последнего чанка после ошибки
   не переопределяет параметры. Публикация manifest должна быть атомарной.
4. Legacy manifest без snapshot не дополнять свежими настройками молча:
   вернуть 409 `upload_snapshot_missing`, сохранить части и предложить явный
   перезапуск загрузки под новым ID.

Fingerprint строится только по исходным encoding-полям, metadata,
resource-параметрам, `catalog_revision` и сведениям о пропущенных значениях.
Исключить binary чанка, `chunk_number` и остальные транспортные поля; имя
и количество частей проверяются отдельно. Fingerprint не должен зависеть
от изменяемых defaults/nickname после первого чанка.
Размеры файлов, существующая проверка безопасности chunk
и сохранность частей при ошибках остаются обязательными.

В серверной пачке одного HTTP-запроса snapshot общий для всех Jobs.
Браузерная пачка из нескольких HTTP-загрузок в MVP может частично завершиться:
после смены каталога новые `file_id` со старой версией получают 409, клиент
останавливает непринятый остаток и предлагает применить новый каталог перед
повтором. Уже начатые файлы завершаются с прежним snapshot. Таким образом,
принятые Jobs одной отправки не получают смесь разных версий пресетов.
Бесшовное продолжение новых файлов по старой версии требует отдельного server
encode-plan и отложено за пределы первой версии.

Старые API-клиенты могут не передавать `catalog_revision`: snapshot выбирается
на начало логического запроса, для chunk — на первую принятую часть.
Изменённые поля формы с `preset_modified=true` также фиксируются один раз,
но не сохраняются в каталоге без действия в редакторе.

Для internal encode с `request_id` сначала выполнить существующую проверку
квитанции. Повтор завершённого запроса возвращает сохранённый ответ, даже если
каталог обновлён/удалён. Revision не добавлять к fingerprint повторно из текущих
данных сервера: отпечаток определяется переданным запросом, как сейчас.

## 10 Пользовательский интерфейс и обновление вкладок

В списке показывать название, ID, краткие параметры, источник, default,
доступность, изменение поставки и отсутствие базы. Редактирование builtin
сопровождать текстом «Изменения будут сохранены в вашей версии пресета».
Название кнопки сохранения — «Сохранить», копирования — «Сохранить как новый».

Форма содержит общие поля и параметры своего слоя. Auto — явный вариант
с подсказкой о непередаче флага; очистка optional поля не восстанавливает старое
значение. Ошибки показываются рядом с полем, ввод сохраняется после сетевого
сбоя или конфликта. До успешного ответа нельзя показывать «Сохранено».

При 412 оставить черновик и предложить перечитать актуальную версию и сравнить
изменения. Автоматически повторять PUT поверх новой версии нельзя.
При удалении default предложить замену до отправки запроса. Сброс и полная
замена импортом требуют отдельного подтверждения с перечислением последствий.
При уходе со страницы с несохранённым вводом показать предупреждение.

После commit отправлять Socket.IO событие `presets_updated` с
`{catalog_revision}`. При восстановлении соединения, фокусе вкладки и видимом
HTTP fallback проверять каталог не чаще одного раза в 5 секунд. Потерянное
событие не должно оставлять вечный устаревший кэш. Очищать удалённые записи
во всех соответствующих caches, а не только дописывать новые.

Для нетронутой главной формы обновить поля выбранных ID либо применить новые
defaults, если пользователь ещё ничего не выбирал. Если выбранный ID удалён,
заблокировать запуск до явного выбора. При ручных изменениях/несохранённом вводе
сохранить форму и показать, что каталог изменился; нужна явная команда применить
его перед новым encode. Во время отправки пачки поля и её revision не менять.

Применять к форме серверный результат `/api/presets/resolve`, включая реальные
subtitles/data defaults и очищенные null audio-поля. Не дублировать merge
хардкодами в `applyLayerSettings()`. Устаревший ответ resolve не должен
перезаписать более новый выбор: использовать номер запроса/отмену запроса.
Поля, разрешённые редактором, должны представляться главной формой, включая
вариант auto и допустимые значения bitrate/sample_rate вне старых select.

Проверить клавиатуру, подписи полей, aria-live для результата сохранения,
светлую/тёмную темы, ширины 395 и 1280 px без горизонтального переполнения.

## 11 Миграция существующих установок

### 11.1 Порядок первого перехода

До первого обновления пользователь останавливает создание новых заданий,
дожидается завершения активных и архивирует фактически используемые `presets/`
и `settings` во внешнюю папку. Для Docker без mount выгружает старый каталог
из ещё существующего контейнера до его пересоздания. Сохраняет версию checkout
или образа и сведения о mount. Наличие архива проверяется до смены поставки.
Инструкции должны охватывать Git/Linux, Docker registry, Windows и Unraid.

В новом релизе предусмотреть CLI без импорта `app.main`:
`python -m app.preset_migration preview --source <архивный каталог>` и
`python -m app.preset_migration apply --source <архивный каталог>
--preview-digest <digest> --if-match <catalog_revision>`.
Это планируемые команды. Запускать при остановленном сервере;
путь user store берётся из той же конфигурации.

`preview` только читает и показывает источники, ошибки, конфликтующие ID,
изменения defaults и ограничения схемы, выводит digest и target revision.
`apply` требует эти значения из успешного preview,
повторно проверяет digest источника и target revision; при расхождении прерывается.
Нельзя принимать произвольный путь через открытый HTTP endpoint.

### 11.2 Правила переноса

Сохранить архив исходных YAML и отчёт. Парсить все четыре слоя, отвергать дубли
и неоднозначные defaults. Нельзя просто пропускать невалидные файлы.
Успешная миграция — атомарная: при ошибке весь действующий каталог остаётся прежним.
После корректировки ошибок пользователь повторяет preview и apply.

Если есть проверяемый эталон **старой** версии, неизменённые определения можно
оставить встроенными, а отличающиеся импортировать полными `override`.
Если такого эталона нет, консервативно перенести все действующие определения
полностью: совпавшие с новыми встроенными ID как override с неизвестной старой
базой, остальные как custom. Это сохраняет старое поведение, хотя закрепляет
и часть старых стандартных настроек. Сравнение только с новой поставкой
не позволяет достоверно определить происхождение отличий.

Defaults legacy каталога перенести как явный выбор, даже если они совпадают
с defaults новой поставки. Существующие ID сохраняются. Сначала материализовать
семантику старого loader: у audio пропущенный codec означает `copy`, audio_map —
`0:a?`; у subtitles пропущенные codec/map означают `copy`/`0:s?`, у data —
`copy`/`0:t?`. Отсутствующие video optional и не имевшие старого default поля
нормализуются в null. Значения из новой поставки не подставляются.
Исходные записи с неподдерживаемыми ключами/значениями
остаются в архиве; отчёт должен назвать каждое препятствие переносу.

Digest нормализованного источника и результат записать в `migrations`.
Повторный apply того же источника — без изменений и новой revision.
Если user store уже непустой и источники конфликтуют, не перезаписывать его:
потребовать предварительный merge/replace через просмотр импорта.
Исходные YAML мигратор не изменяет и не удаляет.

### 11.3 Контейнеры и доставка

В штатных Compose убрать `./presets:/app/presets`; существующий том
`settings:/app/settings` оставить. Для явной миграции старый каталог можно
временно подключить read-only как `/legacy-presets`; этот путь не участвует
в загрузке effective каталога. Если старый `/app/presets` всё ещё смонтирован,
показывать предупреждение о необходимости импорта, не считать его поставкой.

Dockerfile получает builtin вместе с `app/` и не кладёт пользовательские данные
в образ. Добавить `settings/`, резервные копии и runtime user store в
`.dockerignore`, а legacy `presets/` после переноса — в `.gitignore`.
Проверять tracked файлы отдельно: игнорирование не снимает уже отслеживаемые
файлы с учёта. Документация сборки должна исключать локальные пресеты вне
обычных путей из build context вручную.

В dev Compose `./app:/app/app` включает новый builtin каталог; в registry
поставка берётся из образа; Unraid продолжает использовать свой bind `settings`.
В тестовом Compose user store должен находиться в `test_settings`, а не в
боевом томе. Настройки пользователя нельзя добавлять в Git через механизм
первой инициализации или копировать поверх существующего user store при старте.

## 12 Резервирование и совместимость схемы

Для повреждённого user store предусмотреть offline команду
`python -m app.preset_migration restore --backup <файл> --target-digest <sha256>`.
Сервер должен быть остановлен. Команда сверяет SHA256 текущего файла с ожидаемым,
сохраняет повреждённый оригинал отдельно, валидирует backup относительно текущей
поставки, затем атомарно восстанавливает его с новым UUID. Без валидного backup
ничего не заменяет. Это работает без импорта `app.main` и без корректной revision
повреждённого каталога. Диагностический GET в таком состоянии возвращает 503
с причиной и инструкцией восстановления, без выдуманного catalog_revision/ETag.
Инициализация фасада менеджера должна допускать этот режим, а не обрушать импорт
всего приложения исключением о повреждённом user store.

Экспорт и backup содержат только пользовательский каталог и нужные сведения
о базе override; историю Jobs резервировать существующим способом отдельно.
Не включать в экспорт абсолютные пути источников миграции, логи и медиаданные.
Для восстановления на другой машине импортировать каталог, затем показать
отличия поставки и недоступные кодеки без замены пользовательских параметров.

Каждое будущее изменение формата получает миграцию `schema_version`.
До миграции сохраняется исходная копия; преобразование атомарно.
Неизвестная более новая схема открывается с диагностикой без перезаписи.
Возврат к старой версии приложения не должен очищать новый user store.
Для отката требуется соответствующий backup или релиз с поддержкой этой схемы.

## 14 Этапы выполнения

1. **Хранилище и схемы:** immutable снимки, merge, defaults, atomic save,
   CAS, backups, ошибки старта. Новый store сначала закрывается unit-тестами.
2. **Перенос поставки и legacy:** builtin путь, CLI preview/apply,
   инструкции резервирования до обновления, Compose и build context.
3. **Интеграция заданий:** динамические defaults, snapshot Job, chunk pinning,
   версия browser пачки, неизменяемость internal receipts.
4. **HTTP и UI:** CRUD/default/reset, сравнение поставки, импорт/экспорт,
   уведомления и конфликты вкладок, применение главной формы.
5. **Приёмка:** регрессии, браузер, реальное кодирование, обновление Git
   и пересоздание Docker с сохранением тома.

Этапы можно выпускать внутренними частями, но нельзя объявлять редактор
готовым без миграции и проверки обновления: это основное требование функции.

## 15 Проверки и критерии приёмки

Для реализации добавить `tests/test_preset_store.py`, `test_preset_catalog.py`,
`test_preset_editor_api.py`, `test_preset_migration.py` и JS-тесты редактора;
расширить имеющиеся тесты resolve, batch, upload safety, receipts и восстановления.
Точные имена файлов можно адаптировать к принятой структуре тестов.

Обязательные проверяемые сценарии:

Чистая установка без user store должна выдавать нынешний набор пресетов,
defaults и те же FFmpeg params без записи в builtin каталог. Её исходная
revision стабильна между отдельными запусками preview и apply.

1. **Git:** в изолированном временном репозитории сохранить новый preset,
   override и default; получить commit с изменённым builtin через `git pull`;
   перезапустить. User JSON и пользовательские определения сохранены,
   неизменённые builtin обновлены, override показывает различия поставки.
   `git status` не содержит runtime user данных. Боевой checkout тест не меняет.
2. **Docker:** сохранить данные в томе settings, пересоздать контейнер с новой
   версией builtin. Сохранены пользовательские пресеты/defaults, новый builtin
   виден. Отдельно проверить registry и bind-mount settings, отсутствие старого
   builtin volume и изоляцию test_settings. Такой smoke не заменяется mock-тестом.
3. **Первый переход:** импортировать архив старых изменённых YAML, в том числе
   новый ID и изменённый default; без старого эталона сохраняются полные значения.
   Повтор миграции не меняет данные; конфликт/ошибка не даёт частичного переноса.
4. **CRUD:** создание всех четырёх слоёв, копирование, редактирование builtin,
   rename без смены ID, reset, удаление user, атомарная замена default,
   возврат к default поставки. Builtin нельзя удалить, `none` остаётся пустым.
5. **Поставка:** новая/удалённая база, неизвестная база миграции, ID collision;
   пользовательские параметры не меняются без явного действия. Reset удалённой
   базы запрещён, orphaned определение продолжает работать.
6. **Параллельность:** два клиента сохраняют одну revision — выигрывает один,
   второй получает 412 с сохранённым черновиком. Читающие потоки, в том числе
   на Python 3.15t, не наблюдают частично загруженного каталога.
7. **Диск:** отказ прав, заполнение диска, исключения до и после replace,
   сбой backup, перезапуск после commit. Основной файл является целиком старым
   либо новым валидным JSON. Нет ложного 200 и сброса повреждённого файла в пустой.
8. **История:** Job до изменения/удаления пресета использует прежние параметры
   и подпись до/после рестарта. Старые записи без snapshot читаются без resolve.
   Готовая internal квитанция побитово не меняется после смены каталога.
9. **Defaults:** GET, resolve, upload, internal JSON/form и новые Job используют
   одинаковый текущий default без рестарта. Нет зависимости от прежних `DEFAULT_*`.
10. **Загрузка:** изменить/удалить пресет между чанками, повторить последний чанк
    после ошибки. Job получает snapshot первой части; новые параметры с тем же
    file_id дают 409 без удаления частей. Legacy manifest и stale новая загрузка
    дают отдельные понятные конфликты. Пачка не смешивает версии принятых Jobs.
11. **Форма:** null действительно очищает preset/crf/x265/audio-поля; серверные
    subtitles/data defaults видны в форме; смена audio на пользовательское
    «Без аудио» отключает также subtitles/data. Stereo с copy/без аудио запрещён.
    Недоступный FDK нельзя запустить или незаметно заменить другим кодеком.
12. **Ввод:** дубли ключей/ID, неизвестные поля, Python YAML tags, traversal в ID,
    XSS в названиях, bool/дроби вне схемы, несовместимые codec/map,
    управляющие символы в x265, превышение лимитов и неверные If-Match.
13. **Импорт:** round-trip export/import без потери параметров, preview без записи,
    устаревший preview, merge conflicts, подтверждаемая полная замена,
    неподдерживаемая схема, новый UUID после восстановления.
14. **UI:** сохранённый черновик при 412/503, повторное подключение без потери
    актуальности, удаление из кэша, защита от запоздавшего resolve,
    клавиатура и отсутствие переполнения на 395/1280 px.

Команды регрессии: `python -m pytest -q tests` и
`node --test tests/js/*.test.cjs` либо `make test`.
Обязательно запустить настоящий smoke через
`RUN_REAL_MEDIA_TESTS=1 python -m pytest -q tests/test_real_media.py`
и добавить в него выбор пользовательского пресета, проверку аргументов/результата
и неизменности ранее созданного задания после редактирования.
Проверить относительные ссылки документации и `git diff --check`.

Функция принимается после прохождения перечисленных сценариев, включая
обновление Git/Docker, и наличия инструкции переноса **до первого обновления**.
